# Компаньон Hermes для Pixel Watch — дизайн

Дата: 2026-11-22
Статус: на ревью
Репозиторий: `hermes-app` (`ru.evgen.hermes`)

## 1. Задача

Часы должны позволять управлять уже запущенным агентом, не доставая телефон: увидеть,
идёт ли ход, отправить короткий промпт голосом, остановить ход, ответить на запрос
агента (clarify/approval).

Устройство-цель: **Pixel Watch 1 (2022), Wear OS 3.5, API 30, Exynos 9110, 294 мА·ч**.
Это не «ещё один экран телефона»: слабый SoC и маленькая батарея задают бюджет
дизайна жёстче, чем возможности платформы.

Пользователь: Евген, один владелец, телефон Pixel 8 с уже установленным
`ru.evgen.hermes` 7.3.

## 2. Что входит и что нет

Входит (v1):
- экран пульта: статус хода, имя сеанса, модель, хвост ответа;
- голосовой промпт в текущий сеанс;
- Стоп (реальный `session.interrupt`, не только отписка от событий);
- Продолжай — повтор последнего промпта, если ход завершился, а работы явно не хватило;
- ответ на pending-запрос агента: clarify (варианты) и approval (разрешить/запретить);
- свайп влево: последние 5 реплик сеанса — чтобы понимать, на что отвечаешь.

Не входит (сознательно, чтобы не раздувать v1):
- список всех сеансов и создание новых;
- расходы, токены, графики;
- работа без телефона поблизости (свой Wi-Fi и токен на часах);
- файлы и картинки;
- полноценное чтение длинных ответов на часах.

## 3. Архитектура

Мозг — телефон. Часы не знают ни адреса шлюза, ни токена, не ходят в сеть вообще.

```
 Pixel Watch                    Pixel 8                          шлюз Hermes
┌──────────────┐   Data Layer  ┌────────────────────┐   HTTPS   ┌──────────┐
│ :wear        │ ────────────► │ :app               │ ────────► │ gateway  │
│  Compose UI  │  /hermes/cmd  │  WearBridgeService │  WebSocket│          │
│              │ ◄──────────── │  ApiClient         │ ◄──────── │          │
└──────────────┘  /hermes/state└────────────────────┘           └──────────┘
```

Обоснование: телефон уже авторизован, держит сокет и знает, какой сеанс открыт.
Часы получают бесплатно всю авторизацию и не тратят батарею на TLS-хендшейки и
переподключения. Токен на часах — это ещё и лишняя поверхность утечки: часы
теряются чаще телефона.

### 3.1 Модули

| Модуль | Тип | Роль |
|---|---|---|
| `:app` | android application, `ru.evgen.hermes` | существующее приложение + `WearBridgeService` |
| `:wear` | android application, `ru.evgen.hermes` | приложение часов |
| `:watchproto` | kotlin jvm | общий кодек протокола, чистый Kotlin, без Android |

`:wear` обязан иметь **тот же applicationId** `ru.evgen.hermes`: Data Layer
доставляет сообщения только приложению с совпадающим именем пакета. Обе сборки
подписываются существующим ключом `~/.hermes/secrets/hermes-android.jks` —
приложения ставятся на разные устройства, конфликта ID нет.

Следствие, о котором надо помнить при отладке: у debug-сборки телефона
`applicationIdSuffix = ".debug"`, значит **debug-телефон с release-часами не
соединится**. Проверяем только парой release/release; если понадобится отладка на
живом устройстве — `:wear` собирается с тем же суффиксом.

`:wear`: `minSdk = 30` (Wear OS 3.5 на PW1), `targetSdk = 34`, Compose for Wear OS.
Телефонный `minSdk = 24` не меняется.

Кодек вынесен в отдельный модуль, потому что его надо тестировать на JVM без
устройства, а дублировать парсер в двух приложениях — гарантированное расхождение
форматов через две правки.

### 3.2 Телефонная сторона

`WearBridgeService : WearableListenerService`
- `onMessageReceived` для пути `/hermes/cmd` — единственная точка входа команд;
- работает в том же процессе, что и UI, поэтому видит `ApiClient`-синглтон
  и текущий сеанс (id последнего открытого сеанса хранится в `prefs`, его пишет
  `ChatActivity`);
- ответы шлёт через `MessageClient` (`/hermes/result`) и `DataClient`
  (`/hermes/state` — последнее состояние, доступно часам даже если они были
  выключены в момент отправки).

Обработка команд:

| cmd | что делает телефон |
|---|---|
| `send` | `ApiClient.streamTurn(sessionId, text)` в `Dispatchers.IO`, события хода → state |
| `stop` | `ApiClient.stopTurn(sessionId)` — тот же путь, что кнопка «Стоп» в чате |
| `resume` | повторить последнее пользовательское сообщение сеанса, только если `phase = idle` |
| `approve` / `deny` | `answerApproval(requestId, choice)` |
| `answer` | `answerClarify(requestId, qid, text)` |
| `refresh` | отправить state немедленно (часы проснулись) |
| `transcript` | последние N реплик через `ApiClient.messages()` |

Никакого `startService`-жизненного цикла: `WearableListenerService` поднимает
система, отдельный foreground-сервис не нужен.

### 3.3 Состояние

Единая структура, которую понимают обе стороны (`watchproto.WatchState`):

```
phase: idle | running | waiting | error
sessionId, sessionTitle, model
tail: последние 2 непустые строки ответа (обрезаны до 120 символов каждая)
elapsedSec: сколько идёт ход
pending: null | {kind: clarify|approval, requestId, title, choices[]}
error: текст последней ошибки
updatedAt: epoch ms
```

Пуш состояния: при смене `phase`, при `Completed`/`Error`, и не чаще одного раза
в 5 секунд во время стрима (дебаунс). Часы при открытии экрана шлют `refresh`
и получают актуальное состояние одним сообщением, не опросом.

## 4. Протокол Data Layer

| путь | направление | механизм | назначение |
|---|---|---|---|
| `/hermes/cmd` | часы → телефон | MessageClient | команда, JSON ≤ 4 КБ |
| `/hermes/result` | телефон → часы | MessageClient | ack/ошибка на конкретную команду |
| `/hermes/state` | телефон → часы | DataClient | последнее состояние |
| `/hermes/transcript` | телефон → часы | DataClient | последние 5 реплик, ≤ 32 КБ |

Ограничения платформы, которые формируют формат: MessageClient — 100 КБ, DataItem —
100 КБ, и оба не гарантируют порядок доставки. Поэтому:
- в каждом сообщении есть `seq` (монотонный счётчик телефона), часы игнорируют
  состояние с `seq` меньше уже показанного;
- transcript режется по бюджету 32 КБ с конца (свежие реплики важнее), каждая
  реплика усечена до 400 символов;
- состояние — идемпотентный снапшот, а не дельта: потеря сообщения лечится
  следующим пушем или `refresh`.

Формат команд:
```json
{"v":1,"cmd":"send","text":"проверь логи","clientTs":1732270000000}
{"v":1,"cmd":"approve","requestId":"req_123","choice":"yes"}
{"v":1,"cmd":"answer","requestId":"req_123","qid":"q0","text":"второй"}
```

`v` — версия протокола. Несовпадение мажорной версии → часы показывают
«Обновите приложение на телефоне», телефон отвечает `result{ok:false,reason:"proto"}`.
Это дешевле, чем отлаживать молчаливое непонимание после обновления одной из сторон.

## 5. Экраны часов

Compose for Wear OS (M3), три экрана + голосовой ввод.

**1. Пульт (главный).**
- строка статуса: `● идёт 2:14` / `○ свободен` / `⚠ ошибка`;
- имя сеанса и модель (мелким, серым, обрезано);
- хвост ответа: две последние строки;
- кнопки внизу: 🎤 (голос), ⏹ Стоп, ↻ Продолжай. Стоп виден только в `running`,
  Продолжай — только в `idle` после завершённого хода.

**2. Запрос агента.** Появляется сама, когда приходит `pending != null`, и вибрирует.
- clarify: текст вопроса + до 4 кнопок с вариантами + «Свой ответ» (голос);
- approval: команда моноширинным, кнопки «Разрешить» / «Запретить».
- после ответа экран закрывается и возвращает пульт.

**3. Лента (свайп влево).** 5 последних реплик, роли помечены цветом, текст
переносится, длинные реплики усечены. Только чтение — никакого ввода.

**Голосовой ввод.** `RecognizerIntent.ACTION_RECOGNIZE_SPEECH` (системный
распознаватель Wear OS, русский поддерживается). Распознанный текст показывается
на экране подтверждения целиком, с кнопками «Отправить» / «Ещё раз» / «Отмена»:
голос на улице ошибается, и отправка без подтверждения — это отправка мусора
в промпт. Никакой собственной модели распознавания в v1.

## 6. Батарея

Правила, которые нельзя нарушать при реализации:
- на часах нет ни одного периодического опроса, ни `Timer`, ни `WorkManager`;
- сетевой активности на часах нет вообще — Data Layer идёт по Bluetooth через телефон;
- стрим ответа не перерисовывается по токену: телефон пушит не чаще 1 раза в 5 с;
- в ambient-режиме экран статичен (статус + время последнего обновления), таймер
  хода не тикает;
- экран гаснет по системному таймауту, никаких `keepScreenOn`.

Ожидаемый расход: часы активны секундами, а не минутами. Основной вклад — сама
вибрация и подсветка экрана, то есть ровно то, что пользователь запросил.

## 7. Безопасность

- Токен и адрес шлюза на часах не хранятся и не передаются;
- Data Layer доступен только приложениям с тем же package name и подписью —
  стороннее приложение команды не подсунет;
- `approval` с часов выполняет ровно то же, что нажатие в телефоне: отдельного
  «доверенного» пути, обходящего подтверждения, не создаётся;
- команды без `sessionId` применяются к текущему сеансу телефона; если текущего
  сеанса нет — `result{ok:false,reason:"no-session"}` и подсказка на часах.

## 8. Сборка и установка

- `settings.gradle.kts`: `include(":wear", ":watchproto")`;
- `build.gradle.kts`: добавляется плагин `org.jetbrains.kotlin.jvm` для `:watchproto`;
- `build.sh wear` → `:wear:assembleRelease`, проверка подписи тем же `apksigner`,
  выкладка `wear-release.apk` рядом с телефонным;
- телефонный APK получает зависимость `com.google.android.gms:play-services-wearable`
  и запись сервиса в манифесте; версия поднимается, публикация — как обычно;
- установка на часы: Wi-Fi-отладка на часах (Настройки → Для разработчиков) и
  `adb connect <ip:5555> && adb install -r wear-release.apk`. Проверю на живых часах.

Порядок обязателен: сначала телефонный APK с мостом, потом часы. Обратный порядок
даст часы, которые не с кем разговаривать, и ложный вывод «не работает».

## 9. Тестирование

JVM-тесты в `:watchproto` (без устройства):
- round-trip кодека для всех 7 команд и всех 4 состояний;
- неизвестный `cmd` и неизвестная мажорная версия → отказ, а не падение;
- transcript: усечение по бюджету 32 КБ сохраняет самые свежие реплики;
- `seq`: устаревшее состояние отбрасывается, новое принимается.

Живая проверка (обязательна, без неё задача не закрывается):
1. запустить ход на телефоне → часы показывают `running` и таймер;
2. нажать Стоп на часах → на телефоне ход реально прерван (`session.interrupt`),
   часы переходят в `idle`;
3. голосом отправить промпт → он появляется в чате телефона как пользовательское
   сообщение и агент отвечает;
4. вызвать approval (`rm -rf` в промпте) → часы вибрируют, «Запретить» реально
   отменяет выполнение;
5. закрыть приложение на телефоне → часы показывают `idle`, а не висят на старом
   `running` (проверка протухшего состояния).

## 10. Риски и как их снимаем

| риск | следствие | решение |
|---|---|---|
| Data Layer не поднимается между PW1 и Pixel 8 | часы «мертвы» | проверяем на живом устройстве первым делом, до UI: минимальный ping-экран |
| Wear OS 3.5 не поддерживает нужную версию Compose for Wear | сборка падает или UI ломается | фиксируем версии под API 30, проверяем на устройстве |
| PW1 не тянет Compose-анимации | лаги, жор батареи | никаких анимаций кроме вибрации; список — обычный `LazyColumn` |
| телефон убивает процесс, мост не отвечает | часы показывают старьё | `updatedAt` + порог 90 с: старше — показываем «нет связи с телефоном» |
| системный распознаватель не понимает русский на часах | голосовой ввод бесполезен | проверяем на устройстве; fallback — ввод через мини-клавиатуру (Wear-клавиатура) |

## 11. Этапы

1. **Каркас и связь.** `:watchproto`, `:wear` с одним экраном ping, `WearBridgeService`
   с `refresh`/state. Цель этапа — доказать, что Data Layer работает на PW1.
2. **Пульт.** Статус, таймер, Стоп, Продолжай, дебаунс состояния.
3. **Голос.** Распознавание, экран подтверждения, отправка промпта.
4. **Запросы агента.** clarify и approval, вибрация, возврат на пульт.
5. **Лента.** 5 реплик, усечение, кеш на часах.
6. **Живой прогон** по сценарию раздела 9 и публикация обоих APK.

Каждый этап — отдельная карточка в Kanban, этапы 2–5 не начинаются до закрытия
этапа 1: если Data Layer на этой паре устройств не работает, весь остальной
дизайн придётся менять, и делать его заранее — выброшенная работа.
